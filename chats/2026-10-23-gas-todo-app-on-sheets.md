## 文脈

- 2026-10-23 の雑談。職場で約 2 時間半かけ、Google Apps Script (GAS) で
  Todo アプリを作ったという報告。
- 構成は Google スプレッドシート、Google Tasks、Google フォームの 3 つ。
  有料サービスや外部 DB を足さず、無料枠内で実用レベルまで持っていった。
- 本人の評価は「普通に使える感じになった」。

## 構成（本人の説明）

- スプレッドシートを原本（source of truth）とする。
- Google フォームから新しい Todo を登録する。
- スプレッドシートと Google Tasks を、GAS のスクリプト URL から
  定期実行して同期する。
- 競合時は上書きせず、退避側に倒す挙動にした。
- 無料で組み上げた。

未確認:

- トリガー間隔と、競合判定に使うキー（行 ID か Tasks の ID か）。
- フォーム送信の重複排除方法。
- 完了・削除をどちら側の状態として扱うか。

以下は構成からの推測を含む。実装の事実確認は別途必要。

## 2 時間半で実用に届いた理由（推測）

- UI・認証・通知を作らず、マネージドサービスの既存 UI をそのまま使った。
- 原本を 1 つに固定し、同期を「双方向の突き合わせ」ではなく
  「片方向の反映」に寄せた。
- 競合を解こうとせず、退避で回避した。分散合意を実装しない判断。
- ただし「普通に使える」は、単一利用者・小規模・低頻度が前提の評価である。
  共有や同時編集を広げると前提が崩れる。

## 技術メモ（公式ドキュメントで確認）

- 実行時間の上限は 6 分/実行（consumer アカウントと Google Workspace の
  双方）。カスタム関数は 30 秒/実行。時間主導トリガーの合計実行時間は
  consumer で 90 分/日。1 回の同期で扱う件数に上限を設ける必要がある。
- 排他は `LockService` を使う。`getScriptLock()`、`getUserLock()`、
  `getDocumentLock()` があり、`tryLock(timeoutInMillis)` か
  `waitLock(timeoutInMillis)` で取得する。`tryLock` が失敗したら
  その回をスキップする実装は「退避寄り」と相性が良い。
- 定期実行は時間主導トリガー。最短間隔や遅延幅は環境依存なので、
  仕様値ではなく実測で決める。
- Tasks の操作には Advanced Google Services の Tasks API 有効化と
  認可が必要になる。

参照:

- [Quotas for Google Services](https://developers.google.com/apps-script/guides/services/quotas)
- [Class LockService](https://developers.google.com/apps-script/reference/lock/lock-service)

## 設計上の注意（レビュー観点）

- 冪等性: 同じフォーム回答や同じ Tasks を 2 回処理しても重複しない
  キーを持たせる。フォーム回答 ID や Tasks の `id` が候補になる。
- 状態の意味: 「シートから消す」「完了にする」「Tasks から消す」を
  別操作として定義する。削除を同期すると、次回実行で復活する事故が起きやすい。
- 時刻: シートとスクリプトのタイムゾーンを明示する。期限は日付のみか
  時刻付きかを固定し、混在させない。
- トリガー遅延: 定刻の保証はない。最終同期時刻をシートに残し、
  遅延と失敗を後から説明できるようにする。
- 失敗の可視化: 例外を握りつぶさず、エラー行やログシートに残す。
  実行失敗は Apps Script ダッシュボードの実行履歴と突き合わせる。
- 権限境界: 原本シートの共有設定がそのまま権限境界になる。
  フォームの回答先シートと Tasks の認可主体を分けて考える。
- 無料枠: consumer アカウントの割当は Workspace より小さい。
  トリガー合計 90 分/日を意識し、実行間隔と件数を決める。

## 得られた気づき

- 2 時間半の価値は「作り切った」ことより、既存サービスの境界を見極めて
  同期の責務を最小化したことにある。
- 競合解決を実装しないのは妥協ではなく、単一利用者・単一原本という
  前提を明示した設計判断である。
- 小規模な個人・チーム業務は、汎用 SaaS を買うより、
  原本 1 つ + 薄い同期で足りる場合がある。
- 逆に、共有・同時編集・監査が必要になった時点で、
  この構成は限界を迎える。拡張条件を先に決めておく。
