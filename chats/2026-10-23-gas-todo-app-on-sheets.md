- 2026-10-23 の雑談。職場で約 2 時間半かけ、Google Apps Script (GAS) で
  Todo アプリを作ったという報告。
- 構成は Google スプレッドシート、Google Tasks、Google フォームの 3 つ。
  有料サービスや外部 DB を足さず、無料枠内で実用レベルまで持っていった。
- 本人の評価は「普通に使える感じになった」。

## 構成（本人の説明）

- スプレッドシートを原本（source of truth）とする。
- Google フォームから新しい Todo を登録する。
- スプレッドシートと Google Tasks を、GAS のスクリプト URL から
  定期実行して同期する。
- 競合時は上書きせず、退避側に倒す挙動にした。
- 無料で組み上げた。

追記で確認済み:

- 同期は双方向。Tasks 側の削除はシートの中止、完了は完了へ反映する。
- ステータスに応じて行の色を変え、ログシートに操作履歴を残す。
- 閲覧は 3 人程度、編集は本人のみ。

## 2 時間半で実用に届いた理由（推測）

- UI・認証・通知を作らず、マネージドサービスの既存 UI をそのまま使った。
- 原本を 1 つに固定し、同期を「双方向の突き合わせ」ではなく
  「片方向の反映」に寄せた。
- 競合を解こうとせず、退避で回避した。分散合意を実装しない判断。
- ただし「普通に使える」は、単一利用者・小規模・低頻度が前提の評価である。

## 技術メモ（公式ドキュメントで確認）

- 実行時間の上限は 6 分/実行（consumer アカウントと Google Workspace の
  双方）。カスタム関数は 30 秒/実行。時間主導トリガーの合計実行時間は
  consumer で 90 分/日。1 回の同期で扱う件数に上限を設ける必要がある。
- 排他は `LockService` を使う。`getScriptLock()`、`getUserLock()`、
  `getDocumentLock()` があり、`tryLock(timeoutInMillis)` か
  `waitLock(timeoutInMillis)` で取得する。`tryLock` が失敗したら
  その回をスキップする実装は「退避寄り」と相性が良い。
- 定期実行は時間主導トリガー。最短間隔や遅延幅は環境依存なので、
  仕様値ではなく実測で決める。
- Tasks の操作には Advanced Google Services の Tasks API 有効化と
  認可が必要になる。

## 設計上の注意（レビュー観点）

- 冪等性: 同じフォーム回答や同じ Tasks を 2 回処理しても重複しない
  キーを持たせる。フォーム回答 ID や Tasks の `id` が候補になる。
- 状態の意味: 「シートから消す」「完了にする」「Tasks から消す」を
  別操作として定義する。削除を同期すると、次回実行で復活する事故が起きやすい。
- 時刻: シートとスクリプトのタイムゾーンを明示する。期限は日付のみか
  時刻付きかを固定し、混在させない。
- トリガー遅延: 定刻の保証はない。最終同期時刻をシートに残し、
  遅延と失敗を後から説明できるようにする。
- 失敗の可視化: 例外を握りつぶさず、エラー行やログシートに残す。
  実行失敗は Apps Script ダッシュボードの実行履歴と突き合わせる。
- 権限境界: 原本シートの共有設定がそのまま権限境界になる。
  フォームの回答先シートと Tasks の認可主体を分けて考える。
- 無料枠: consumer アカウントの割当は Workspace より小さい。
  トリガー合計 90 分/日を意識し、実行間隔と件数を決める。

## 追記: 双方向同期の状態遷移

- Tasks で完了 → シートは完了へ遷移する。
- Tasks で削除 → シートは中止へ遷移する。
- ステータスに応じて行の背景色が変わる。
- ログシートで誰が何をしたかを追える。
- 閲覧は 3 人程度。編集権限は本人のみ。

Tasks は「完了」と「未完了」しか持たず、中止に相当する状態がない。
削除を中止として解釈するのは、この非対称性を埋めるための写像である。
シート側を消さずに状態だけ変えるため、誤削除でも原本は残る。

## 追記: 双方向同期のレビュー観点

- 削除の判定は「一覧に無いこと」ではなく `deleted` フラグで行う。
  `tasks.list` は `showDeleted=true` を指定しないと削除済みを返さない。
  一覧の欠落を削除とみなすと、API の一時失敗やページング漏れで
  全行が中止になり得る。
- `hidden` を削除と混同しない。完了済みタスクを一覧からクリアすると
  `hidden=true` になるが、これは削除ではない。中止に落とすと誤遷移する。
- 完了は `status === "completed"` と `completed` の時刻で判定する。
  中止は Tasks 側に状態がないため、削除以外の表現ができない。
- 打ち返し（ping-pong）を防ぐため、シートに Tasks の `updated` を保持し、
  差分がある場合だけ書き込む。Tasks は `etag` を持つので、
  更新時は `If-Match` 相当の条件付き更新を使う。
- 行の色は条件付き書式で付ける。スクリプトから `setBackground` すると
  条件付き書式や手動編集と衝突し、実行ごとに全行を塗り直すことになる。
- 「誰が」の記録には限界がある。Tasks API は最終更新者を公開しないため、
  Tasks 側の操作を個人に帰属できない。`updated` は時刻のみ。
- シート側の操作者をログに残すなら、単純トリガーの `onEdit` では
  `Session.getActiveUser().getEmail()` が空になり得る。インストール可能な
  トリガーを使う。トリガー実行時の `getEffectiveUser()` は設定者を返す。
- 期限は Tasks API では日付のみ。時刻を書いても破棄されるため、
  シート側も日付単位で扱う。
- 閲覧者に編集権限を渡すと「単一編集者」の前提が崩れる。
  シートの範囲保護か共有設定で読み取り専用を徹底する。
