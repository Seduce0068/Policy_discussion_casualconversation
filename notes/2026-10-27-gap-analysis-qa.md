## 目的

- 設計書とソースの乖離を、深刻度と対応方針で分類する。
- 意図が不明なものは推測で埋めず、QA（Question & Answer）として出力する。
- QA の回答を設計書とテストに反映し、移行の判断根拠を残す。

## 乖離の分類

| 分類 | 定義 | 対応 | 例 |
| --- | --- | --- | --- |
| 設計書が正 | ソースが設計書と違う | ソースを修正する | 必須チェックが実装されていない |
| ソースが正 | 設計書が古い | 設計書を修正する | 項目が追加されているのに設計書にない |
| 両方違う | 業務ルールが変わった | 業務担当が正を決める | 端数処理が設計書と実装で違う |
| 意図不明 | どちらが正か判断できない | QA に出す | 例外処理の意図が読めない |
| 死んだ仕様 | 設計書にあるがソースにない | 削除候補にする | 使われていない画面、項目 |
| 暗黙仕様 | ソースにあるが設計書にない | 設計書に追記する | 隠し項目、特殊な分岐 |
| 用語の揺れ | 同じ意味で違う用語 | 用語集に統合する | 「顧客」と「取引先」 |

## 深刻度

| 深刻度 | 基準 | 対応期限 | 例 |
| --- | --- | --- | --- |
| Critical | 金額、法令、セキュリティ、締め処理、業務停止 | 即日 | 消費税の計算が違う |
| High | 画面の振る舞い、帳票、外部 IF | 1 週間 | 承認後の編集可否が違う |
| Medium | 表示・非表示、バリデーション、エラーメッセージ | 2 週間 | 文字制限が設計書と違う |
| Low | 文言、レイアウト、ログ | 1 ヶ月 | エラーメッセージの表現 |
| Info | コメント、用語、古い記述 | 次回更新時 | 設計書の更新日が古い |

## QA に出す条件

- 設計書に記述がない。
- 設計書とソースが違うが、どちらが正か判断できない。
- 業務ルールが複数解釈できる。
- 例外処理の意図が不明。
- 死んだコードか現役のコードか不明。
- 外部 IF の仕様が不明。
- 過去の改修履歴が不明。
- 業務担当の確認が必要。

## QA の項目

| 項目 | 内容 |
| --- | --- |
| QA ID | `QA-001` 形式 |
| タイトル | 1 行で内容を表す |
| 発見日、発見者 | いつ、誰が発見したか |
| 関連資産 | 設計書、ソース、画面、バッチ、帳票、DB |
| 乖離の内容 | 設計書とソースの差分 |
| 深刻度 | Critical / High / Medium / Low / Info |
| 質問 | 何を確認したいか |
| 選択肢 | A / B / C と推奨 |
| 回答者 | 業務担当、設計者、運用担当 |
| 期限 | 回答を得る日 |
| ステータス | Open / In Progress / Answered / Deferred / Closed |
| 回答 | 回答の内容 |
| 決定 | 設計書を直す、ソースを直す、現状維持、保留 |
| 影響範囲 | 移行対象、テストケース、リリース |
| 関連チケット | Issue、PR |

## QA の出力形式

- 一覧は `docs/qa/qa-list.md` に置く。
- 詳細は 1 QA 1 ファイル `docs/qa/QA-001.md` に置く。
- 一覧の列は ID、タイトル、深刻度、ステータス、期限、回答者にする。
- 詳細には質問、選択肢、推奨、回答、決定、影響範囲を書く。
- front matter に OKF のメタデータを付ける。
- 回答が得られたら、設計書とテストに反映し、QA をクローズする。

## QA の運用

- 週次でレビュー会を開き、Open と In Progress を確認する。
- 回答者を明確にし、期限を決める。
- 回答が得られない場合は「保留」とし、移行対象から外すか現状維持で進める。
- 回答を設計書に反映し、テストケースに追加する。
- クローズ条件は、設計書とソースのどちらを正とするか決まり、テストで固定されたこと。
- Critical と High は、移行のパイロット対象から外さない。

owner: "業務担当"
due: "2026-11-10"

## 質問

## 選択肢

- A: 編集できない。設計書が正。
- B: 編集できる。実装が正。
- C: 条件付きで編集できる。条件を定義する。

## 推奨

A。監査上の観点から、承認後の編集は不可とする。
