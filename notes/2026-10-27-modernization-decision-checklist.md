## 目的

- Spring Boot + Doma 3 + Markdown 化の方針は決まった。
- ここでは、移行の設計と運用に影響する残りの決定事項を、優先度別に整理する。
- すべてを同時に決めない。設計の前提になるものから順に決める。

## 決定済み

| 項目 | 決定 |
| --- | --- |
| アプリケーション基盤 | Spring Boot 4.x |
| Java | Java 25 LTS |
| JDK | Azul Zulu 25（無償版） |
| O/R マッパー | Doma 3 |
| 設計書 | Markdown を SSOT |
| 移行方式 | ストラングラー |
| 移行主体 | 内製。外部は短期レビュー |
| 有償サポート | 必須としない。本番で SLA が必要になった時点で検討 |

## 今すぐ決める（設計の前提）

| 項目 | 選択肢 | 推奨 | 理由 |
| --- | --- | --- | --- |
| DB | 既存維持 / PostgreSQL | 既存維持を基本 | DB 移行はリスクが大きい。新規サービスだけ PostgreSQL も可 |
| ビルドツール | Maven / Gradle | Maven | 既存資産と Spring Boot の標準。Wrapper で再現性を確保 |
| DB マイグレーション | Flyway / Liquibase | Flyway | SQL ベースで差分が読みやすく、レビューしやすい |
| 認証・認可 | 既存 LDAP/AD / OIDC | 既存基盤を Spring Security で接続 | 認証基盤の変更は全画面に影響する |
| セッション | Redis / JDBC / インメモリ | 要件で判断 | 水平分散なら Redis、単一ノードなら JDBC |
| 画面 | Thymeleaf / React | 画面単位で判断 | 変更頻度と複雑さで決める。一括 SPA 化はしない |
| 帳票 | JasperReports / Excel テンプレート | 帳票の複雑さで判断 | 既存 Excel 資産を活かすならテンプレートを維持 |
| バッチ | Spring Batch / 既存基盤 | Spring Batch | ジョブ定義の外部化、再実行、進捗管理 |
| アーキテクチャ | レイヤード / モジュラモノリス | モジュラモノリス | 段階移行の境界を明確にし、後で分離しやすくする |
| CI/CD | GitHub Actions / 既存 | GitHub Actions | 再利用可能ワークフローでゲートを共通化 |
| コンテナ | Docker / Podman | 環境に合わせる | オンプレは Podman、クラウドは Docker も可 |

## 移行設計で決める（データと業務）

| 項目 | 決めること | 推奨 |
| --- | --- | --- |
| 文字コード | UTF-8 に統一するか、既存の Windows-31J を残すか | UTF-8。既存データは変換時に件数と文字化けを検証 |
| タイムゾーン | UTC 保存か、Asia/Tokyo 保存か | UTC 保存、表示時に Asia/Tokyo へ変換 |
| 排他制御 | 楽観ロック / 悲観ロック | 楽観ロックを基本。競合が多い画面だけ悲観ロック |
| 監査ログ | 誰が、いつ、何を、どこから | 構造化ログと DB 監査テーブルを併用 |
| 外部 IF | SOAP / REST / ファイル | 既存を維持し、新規は REST。SOAP は Spring Web Services |
| データ移行 | NULL、日付、暗号化、桁数、丸め | 移行リハーサルで件数とサンプルを突合 |
| 個人情報 | マスキング、保持期間、削除 | ログと画面でマスキング。保持期間を先に決める |
| 性能 | ベースライン、目標値、負荷試験 | 移行前に現行のベースラインを測る |

| 体制 | 内製 / ベンダー、教育 | 内製 + スポットレビュー。属人化を避ける |

## 初期セットアップの順序

全体を一括で変換しない。1 機能ずつ「設計書の MD 化 → ソース解析 →
トレーサビリティ → 特性テスト → 乖離レビュー → 移行」を垂直に進める。

1. 棚卸し: ソース、設計書、DB、外部 IF、バッチ、帳票の一覧と容量。
2. ビルド再現: 現行をローカルと CI でビルドし、テストを実行。
3. ドキュメント基盤: AGENTS.md、README、用語集、ADR、Runbook。
4. 設計書の MD 化パイロット: 1 機能分の設計書を変換し、OKF を付与。
5. トレーサビリティマップ: 設計書とソースを ID で紐付け。
6. 特性テスト: 1 画面、1 バッチ、1 帳票の振る舞いを固定。
7. 乖離レビュー: 設計書とソースの差分を分類し、業務担当と確認。
8. パイロット移行: 1 機能を Spring Boot + Doma 3 で移行。
9. 振り返り: 変換パイプラインとテストを改善し、横展開。

### 各ステップの出口条件

| ステップ | 成果物 | 出口条件 |
| --- | --- | --- |
| 棚卸し | 一覧、容量、オーナー、更新頻度 | 全体像が共有されている |
| ビルド再現 | ビルド手順、CI、テスト結果 | CI でビルドが通る |
| ドキュメント基盤 | AGENTS.md、README、用語集 | 新規参加者が 1 日で環境を作れる |
| MD 化パイロット | 1 機能の MD 設計書 | 元 Excel と突合済み |
| トレーサビリティ | 設計書とソースの対応表 | 主要な画面・バッチ・帳票が紐付く |
| 特性テスト | テストコード、ゴールデンマスター | 現行の振る舞いが再現できる |
| 乖離レビュー | 乖離一覧、判断結果 | 業務担当が確認済み |
| パイロット移行 | 1 機能の Spring Boot 実装 | 特性テストが通る |
| 振り返り | 改善点、横展開計画 | 次の 3 機能の計画がある |

### 容量と解析の前提

- ソース 1 GB 未満は、全体像の把握には十分だが、AI のコンテキストには大きすぎる。
  LSP / Serena でシンボル単位に絞り、grep で設定・SQL・JSP を追う。
- Excel は容量より、シート数、セル数、外部リンク、マクロ、画像の棚卸しが重要。
- 変換は 1 ファイルずつ行い、元ファイルのハッシュと変換日時を記録する。
- 設計書とソースに個人情報や秘密情報が含まれる場合、AI に渡す前にマスキングする。
- 閉域要件がある場合は、ローカル LLM を優先する。

### 現行機能の保証

- 設計書だけでは振る舞いを保証できない。設計書にない暗黙仕様を、テストとログで補う。
- 画面は Playwright、帳票は PDF 比較、バッチは入出力比較、DB はスナップショットで固定する。
- 移行前後のシャドーリードで、同じ入力に対する出力の差分を確認する。
- 最終的な受け入れは、業務担当のシナリオテストで行う。

## 人間が担う役割

AI は調査、変換、テスト生成、レビュー補助に使う。次の領域は人間が担う。

| 領域 | 人間がやること | AI に任せられない理由 |
| --- | --- | --- |
| 業務仕様 | 暗黙仕様、例外、端数、締め処理の最終判断 | 業務上の正しさは設計書とコードだけでは決まらない |
| 優先順位 | 移行対象、時期、予算の決定 | ビジネス価値とリスクのトレードオフ |
| 合意形成 | 業務部門、経営層、監査、ベンダーとの調整 | 組織の意思決定と説明責任 |
| 本番操作 | カットオーバー、ロールバック、障害対応 | 不可逆な操作と責任 |
| 契約・法務 | ライセンス、個人情報、監査対応 | 法的判断と契約責任 |
| 品質受け入れ | UAT、シナリオテスト、承認 | 業務の受け入れ責任 |
| アーキテクチャ | 技術選定の最終決定、トレードオフの判断 | 長期的な影響と責任 |
| 組織・教育 | 役割分担、教育、属人化の解消 | 組織設計と人の合意 |

### 人間の判断をボトルネックにしない

- 判断が必要な事項を早期にリスト化し、期限を決める。
- AI で候補を絞り、人間の判断を「はい/いいえ」に近づける。
- 業務担当のレビュー時間を先に確保する。
- 判断結果を ADR と用語集に記録し、再利用する。
- 判断待ちの作業と、判断が不要な作業を分離する。

## 決め方

- 決定には期限を付ける。期限のない保留は決めないのと同じ。
- 決定は ADR に記録する。選択肢、理由、却下理由、影響を残す。
- 業務判断は業務担当、技術判断は技術担当が持つ。
- opencode は選択肢と根拠を出すが、決定は人間が行う。
- 決められない項目は「保留」と「再検討の日付」をセットにする。
