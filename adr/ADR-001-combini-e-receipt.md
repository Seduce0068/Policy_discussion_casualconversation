## ADR-001: コンビニ電子レシート統合アーキテクチャ

### 状態

提案中 (Proposed)

### 背景

日本の大手コンビニチェーン (セブン-イレブン・ローソン・ファ
ミリーマート・セイコーマート・ミニストップ等) では、紙レシート
の発行が依然として主流である。一方で、ユーザー側の指摘にもある
通り、技術的な実装難易度自体は低い。既にスマートレシート (東芝
テック) による実証実験が全国 18,000 店以上で行われ、累計 3 億枚
以上の電子化実績がある。

現在の各チェーンアプリは「会員 ID 認証」「電子マネー決済」「ポ
イントカード提示」の骨格を既に備えている。購買明細の生成・保存
・呼び出しという構造的土台は、以下のように既に存在する。

- 数据の骨格は規約上も全チェーンで備わっている
- スマートレシートの実証モデルが存在する
- 決済/会員 ID 層は既に統合が進んでいる

とはいえ紙レシートが消えていない理由は「技術」ではなく「実装後
の普及成立条件」にある。この文書は、その条件を解決するためのア
ーキテクチャを定義する。

### 事実と制約

#### 検証済み事実 (Runtime Proof)

- **スマートレシート**: 全国 18,000 店以上で稼働、累計 3 億枚。
  参考: <https://www.toshibatec.co.jp/news/release/20260325-01.html>
- **ミニストップ**: 全店でスマートレシート対応済み。
  参考: <https://www.ministop.co.jp/service/smartreceipt>
- **ファミペイ**: FamiPay 決済分の電子レシート閲覧実装済み。
  参考: <https://qa.family.co.jp/famipay/s/article/000009065>
- **経産省標準規格**: KDDI 総研 (2018) で 27 店舗 / 2,700 人参
  加の実証検証済み。
  参考: <https://www.kddi-research.jp/newsrelease/2018/013101.html>
- **セコマ (セイコーマート)**: 会員規約に「購入履歴」取得を明
  示。Pecoma 決済と連動。
  参考: <https://www.seicomart.co.jp/clubcard/scc_kiyaku.html>
- **Air レジ終了** (2026-03-17): 「利用状況を踏まえ」提供終了。
  二重インフラ問題の典型。
  参考:
  <https://faq.airregi.jp/hc/ja/articles/52363060108569>
- **FC 加盟店の IT 更新コスト**: 10 年で 700〜1,200 万円という
  試算が存在し、POS 改修は加盟店負担。
  参考: <https://note.com/fc_databank/n/n32aa52b786ec>
- **紙のコスト構造**: 1 枚あたり数円程度の可変コスト。
- **検索不可の現状**: セブン公式アプリ FAQ には購入履歴・電子レ
  シートの機能が項目として存在せず、nanaco 残高確認は紙レシート
  前提の案内のまま。
  参考: <https://www.sej.co.jp/products/app/faq>
  参考: <https://www.nanaco-net.jp/how-to/menu/confirm.html>

#### 核心的制約

1. **FC 構造**: POS 改修は加盟店負担が原則。本部の正義 (データ
   収集・ブランド統一) と加盟者の負担が乖離しやすい。
2. **opt-in 率**: 会計時にアプリを提示する opt-in 型では、
   opt-in 率が伸びにくい。紙と二重運用が続く。
3. **決済手段の分散**: 現金 / クレカ / 電子マネー / コード決済
   が混在し、決済 ID と会員 ID が必ずしも一致しない。
4. **法務要件**:
   - 電子帳簿保存法 (電子取引データの検索性・訂正削除管理)
   - インボイス制度 (FC 店ごとの登録番号表示)
   - 宛名付き正規領収書への対応 (紙フローが残る)
5. **データ資産の帰属**: チェーン本部は購買データを自社アプリに
   閉じ込める動機が強く、第三者共通アプリへの搬出を嫌がる。

### 決定事項

本アーキテクチャは「紙を消す」ことを第一目標とせず、
**「opt-in 率を上げること」を第一目標**とした最小構成を定義す
る。以下の決定を行う。

#### D-1: 共通 ID レイヤの採用

チェーン横断で動く「共通 ID レイヤ」を設ける。各チェーンの既存
会員 ID (7iD / Ponta / dポイント / FamiPay / Pecoma) をこのレ
イヤにぶら下げ、**1 つのレイヤで複数チェーンの許可制御・履歴保
存・明細管理**を行う。

- **選択した項目**:
  - 共通 ID レイヤ (identity asset pooling)
- **根拠**: 全チェーンで会員アプリ・決済 ID の骨格は既に存在す
  る。新規に ID を発行する必要はなく、既存 ID の紐付けで足り
  る。
- **リスク**: Chain 別のデータ資産の帰属 (本部側าก動機) が障害
  となる可能性。

#### D-2: JDLA 標準フォーマットの採用

購買明細の正規化には、経産省標準規格 (2018 KDDI 総研実証検証済
み) と東芝テック国際標準仕様 (2017 実証) を参照スキーマとして採
用する。

- **選択した項目**:
  - 経産省標準規格 / 国際標準仕様ベースの正規化スキーマ
- **根拠**: 相互運用実績が存在し、チェーン間で共通化可能。
- **リスク**: フォーマットの解釈差 (税区分・ランク付与) による
  相互運用性の不整合。

#### D-3: 決済 ID = 会員 ID の統合 (意味のある opt-in の削減)

「決済 ID = 会員 ID」を前提とすることで、会計時の提示操作を **1
回で完結**させる。決済バーコードと会員バーコードを同一化するこ
とで opt-in の宥めすかし (負担) を軽減する。

- **選択した項目**:
  - 決済 ID と会員 ID のびり統合 (single-table identity)
- **根拠**: 現状は「ポイントカード提示」「バーコード決済」「ク
  ーポン提示」の 3 操作が分散しており、UX 負荷が opt-in 率の伸
  び悩みの原因となっている。
- **リスク**: 現金・クレカ決済などの**通知型でない決済**では容
  易ではない。チェーンにより対応梯度が異なる。

#### D-4: 紙の UI 再現と既存レシートインフラの併存

紙レシートと電子レシートの**並行運用を原則**とし、電子レシート
は opt-in 型として提供する。紙レシートの UI (明細項目・構成) を
そのまま電子で再現する。

- **選択した項目**:
  - 紙との並行運用 (opt-in 型)
  - 電帳法上「紙のまま転記した内容の電子化」
- **根拠**: opt-in 率が伸びるまで紙は消えない。強制的な紙廃止
  は控える。
- **リスク**: 二重インフラが固定費として残る (Air レジ終了の前
  近例)。

#### D-5: 既存アプリへの画面追加

**新規アプリを作らない。** 各チェーンの既存アプリに「電子レシ
ート」閲覧画面を追加する形で実装する。

- **選択した項目**:
  - 各チェーンアプリ内に電子レシート閲覧 UI を追加
- **根拠**: ファミペイは既にこのパターンで実装済み。チェーンア
  プリは既に利用者ベースを持っているため、新規会員獲得コストな
  く広がる。
- **リスク**: 中央センタ側の固定コストが存在し、チェーンによって
  は継続提供の意思決定が揺らぐ可能性 (Air レジの例)。

#### D-6: センター (中央ゲート) の構成

電子レシートセンターを **チェーン横断の中立ゲート**として設け、
明細の正規化・検索性・訂正削除管理・配信を担う。チェーン本部は
センターへの搬出データを選択する。

- **選択した項目**:
  - 引き剥がし型の中央ゲート (chain-neutral)
- **代替案**:
  - チェーン個別の取り置き型単品レシートセンター (全チェーン手
    作り、相互運用性なし)
  - 共通アプリ型 (kvitanco 様式・本部のデータ資産化意愿と衝突)
- **代替を却下した根拠**:
  - 単品型は相互運用性がなく本部の投資対効果も弱い
  - 共通アプリ型は本部のデータ資産化意志に矛盾し、実現確率が低
    い
- **リスク**: センター側の保管・検索要件対応コストの固定化。

### アーキテクチャの全体構成 (v2)

```text
    [既存アプリ]                              [紙レシート]
  ┌─────────┐                                ┌─────────┐
  │セブン7iD│                                 │  現行の │
  │(Ponta)  │                                │ 継続運用 │
  │(FamiPay)│                                └─────────┘
  │(Pecoma) │
  └────┬────┘
       │
       ▼
   [共通 ID レイヤ]
       │
       ├─1 会員/決済 ID 統合 (D-3)
       │
       ├─2 購買明細の正規化 (D-2 / JDLA 標準)
       │
       ├─3 電子レシートセンターで保管
       │  (電帳法要件の検索性 + 訂正削除管理)
       │
       └─4 各チェーンアプリの UI で閲覧 (D-5)
```

### 法務要件と実装の対応

| 法務要件 | 実装位置 | 実装方針 |
| --- | --- | --- |
| 電子帳簿保存法 (検索性・訂正削除管理) | レシートセンター | 電子取引として一元保存し、検索性を担保 |
| インボイス制度 (登録番号表示) | レシートデータ | FC 店ごとの登録番号をトランデータから流用 |
| 登録番号なしの対処 | レシートデータ | トランデータの生データを基底として保持 |
| 宛名付き正式領収書 | 複写 UI | 紙出力と同じ項目を電子で表示 (領収印への置換含む) |

### アーキテクチャへの影響

**前提として全体の実装を期日ベースに管理する場合:**

- **Phase 0 (4 週間)**: センターの骨格構築・JDLA スキーマの来歴
  記録
- **Phase 1 (8 週間)**: セコマ・ファミマの実装 (Pecoma /
  FamiPay 決済ベース)
- **Phase 2a (8 週間)**: 本部側アプリ内の「電子レシート」表示 UI
  生成。セブン・ローソン含む。
- **Phase 2b (12 週間)**: FC 加盟店側 POS 改修の同意・fee 配分合
  意の取得。Phase 2a 完了が開始条件。技術工程から契約工程へ放出
  の boundary。詳細:
  `reports/e-receipt-feasibility-report.md` §7.2
- **Phase 3 (12 週間以上)**: opt-in 率 KPI の評価と紙廃止の判断

**複数チェーン同時实现を述べる場合、実装難度の非対称性**:

| チェーン | 接点の実装難度 | 推定工数 |
| --- | --- | --- |
| セブン | 低 (7iD 決済ベース) | 1〜3 か月 |
| ファミマ | 低 (FamiPay ベースで段階的) | 1〜3 か月 |
| セコマ | 最小 (規約に購入履歴明示済み) | 1〜3 か月 |
| ローソン (Ponta) | 中 (明細管理の整備が必要) | 3〜6 か月 |
| ミニストップ | 既存 (スマートレシート接続済み) | 完了 |

### KPI 評価基準 (紙レシート廃止の判断ライン)

本アーキテクチャは、opt-in 率が以下の局面に到達した段階で管
理・判断される。

1. **局所上限の到達**: 「会計時の提示操作が 1 回で完結する (決
   済 ID = 会員 ID)」条件下での opt-in 率が 60% を超える
2. **opt-in 率 95%**: この到達以前は紙レシートの廃止を禁止し
  、「紙と電子の二重運用」を原則として認める
3. **紙の廃止自体は新たに別の ADR で判断する**

### リスクと緩和策

| リスク | 緩和策 |
| --- | --- |
| FC 加盟店が桁違いの POS 改修を拒否する | 既存 POS の帳票並列出力追加のみで済む設計 |
| opt-in 率が伸びない | 決済 ID = 会員 ID の統合で提示を 1 回に |
| 二重インフラの固定費 (Air レジ型) | 電子パスが IIR を向上させた段階で selon 段階的に紙を後退させる |
| 本部側がデータ搬出を嫌がる | 本部は自身のアプリ内データ集約を維持し、センターは中立ゲートとして分離 |
| JDLA スキーマ解釈の差異 | センター側で正規化層を追加し、チェーン別スキーマ変換を集約 |
| 現金決済の ID 取得 | 会員提示型 opt-in を認め、紙と並行を原則とする |

### 選択肢と論点の残り

本 ADR は以下の項目を**スコープ外**としている。

- 紙レシート廃止の期日 (別 ADR で判断)
- ポイント連携の強度 (別 ADR)
- 本部側マーケティング DB 利用の推進・制限 (別 ADR)
- 現金決済手持での ID 取得の義務化 (別 ADR)
